Debian OpenVPN & MITM

Ataque MITM (SSL Strip) vs. túnel OpenVPN

$ ettercap SSL Strip → OpenVPN server → cliente Windows → túnel neutraliza o MITM

AutorDavid Manuel
ContextoSegurança Informática — Trabalho prático

Rede montada no VirtualBox: Kali (atacante), Debian 10.10.10.1 com o site DVWA e o servidor OpenVPN (túnel 10.8.0.1), Windows 7 (vítima do ataque) e Windows 10 (cliente VPN). Sem VPN o ataque apanha o login; com o túnel activo, deixa de apanhar.

1

Ataque de SSL Strip a um login em HTTPS

ettercap -T -q -i eth0 -M arp:remote /10.10.10.1// /10.10.10.7//  (SSL Intercept + ARP poisoning)

Usei o ettercap no Kali (SSL Intercept + ARP poisoning) contra o login do DVWA: sem VPN, o utilizador e a password apareceram em claro no atacante.

2

Instalar/configurar Servidor OpenVPN no Linux Debian

openvpn --config server.conf  (rede 10.8.0.0/24, porta 1194/udp, tls-auth)

O servidor OpenVPN corre no Debian: rede 10.8.0.0/24, porta 1194/udp, tls-auth, ip_forward activo e UFW com as portas 1194/udp, 22, 80 e 443 abertas.

3

Instalar/configurar cliente OpenVPN no Windows 10

OpenVPN GUI → client.ovpn + ca.crt + aluno01.crt/key + ta.key

No Windows 10 instalei o OpenVPN GUI e usei a configuração cliente VPN (client.ovpn + ca.crt + aluno01.crt/key + ta.key). A ligação subiu e a placa TAP ficou com o IP 10.8.0.6.

4

Login pelo túnel VPN — o MITM já não apanha nada

https://10.8.0.1/dvwa  (login pelo IP do túnel, nunca pelo 10.10.10.1)

Com o mesmo ataque ativo, fiz login no DVWA pelo https://10.8.0.1/dvwa (o IP do túnel, nunca pelo 10.10.10.1). O login funcionou, mas o atacante só vê tráfego cifrado.

// notas rápidas

Conclusão: o túnel OpenVPN cifrada todo o tráfego entre o cliente e o servidor, pelo que o ARP poisoning + SSL Strip do ettercap deixa de conseguir decifrar o login. O tráfego que passa pelo atacante é apenas OpenVPN cifrado (P_DATA_V2), indecifrável sem a chave do túnel.
